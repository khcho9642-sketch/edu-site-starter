# [강좌] C18. 브랜치와 PR — 본편 안 건드리고 실험하기

> Claude Desktop 앱 전체 기준 · Windows 중심 · 공식 문서 확인: 2026-11-14
> 실습 화면: Desktop의 Code 화면 + GitHub 웹의 Pull requests 탭
> C17의 커밋·푸시 실습을 마친 뒤 읽습니다. 새 브랜치에서 변경하고 PR(변경 제안)을 읽는 법에 집중합니다.

> 먼저 읽을 강의: C17.

## 3줄요약

1. 실험은 **새 브랜치**에서 하고, main(본편)에는 **PR로 검토한 뒤** 합친다.
2. PR은 "이렇게 바꿀게요" 제안서다. **변경 내역(Files changed)을 읽고** 머지한다.
3. 충돌이 나면 한쪽을 통째로 덮지 말고 **양쪽을 비교한 설명**부터 받는다.

## 1. 준비와 오늘의 결과

C17에서 푸시한 `my-gagyebu-practice`를 쓴다. 오늘 결과는 **연습 PR 1개를 만들고, 변경 내역을 읽은 뒤 머지한 기록**이다.

## 2. 브랜치에서 작업하고 PR 만들기

1. Code 화면에서 연습 폴더 세션을 연다. 앱에 세션별로 별도 작업 공간(워크트리·브랜치)을 만드는 선택지가 있으면 그것을 써도 된다. 표시는 버전마다 다를 수 있다.
2. 새 브랜치에서 작은 변경을 요청한다.

> main은 그대로 두고 새 브랜치 add-category-total을 만들어줘. 거기서 지출샘플.csv의 카테고리별 합계를 README에 표로 추가해줘. T004는 미확정으로 표시하고 0원으로 바꾸지 마.

3. 커밋과 푸시 후 PR을 요청한다.

> 이 브랜치를 푸시하고 main으로 가는 PR을 만들어줘. PR 설명에는 무엇을 바꿨는지, 어떻게 확인했는지, 미확정 항목을 적어줘.

4. GitHub 웹 → **Pull requests** 탭에서 방금 만든 PR을 연다.

## 3. PR 읽는 법과 머지

| PR 화면 영역(이름은 바뀔 수 있음) | 볼 것 |
|---|---|
| 설명(Conversation) | 무엇을, 왜, 어떻게 확인했는지 |
| 변경 파일(Files changed) | 빨간 줄 = 삭제, 초록 줄 = 추가. 안 시킨 파일이 바뀌었는지 |
| 체크(Checks) | 자동 검사 결과(C19) |
| 머지 버튼 | 위를 다 본 뒤에 누른다 |

- 변경 파일에 **요청하지 않은 파일**이 있으면 머지하지 말고 이유를 묻는다.
- 합계 숫자는 `지출샘플.csv`로 직접 계산해 대조한다. 확정 5건(T001·T002·T003·T005·T006) 합계 **28,000원**, T004는 미확정이어야 한다(C06와 같은 기준).

**충돌이 났을 때**

> 충돌이 났어. 양쪽 내용을 나란히 비교해서 설명해주고, 어떻게 합칠지 추천만 해줘. 내가 OK하기 전엔 고치지 마.

## 4. 주의 사항

- main에 직접 푸시하는 습관을 들이지 않는다. 작은 변경이라도 PR로 연습한다.
- PR 설명에 개인정보·비밀값을 쓰지 않는다. PR은 저장소 접근자 모두가 본다.
- 머지는 되돌리기 번거롭다. **변경 파일을 읽은 뒤** 누른다.
- 자동으로 머지되게 하는 설정은 연습 단계에서 켜지 않는다.

## 5. 이렇게는 쓰지 말자

| ❌ 이렇게 하지 말자 | ✅ 대신 이렇게 | 이유 |
|---|---|---|
| "main에 바로 올려" | "새 브랜치에서 하고 PR 만들어줘" | 실수가 바로 본편에 들어간다 |
| PR을 열자마자 머지 | Files changed를 끝까지 읽고 머지 | 안 시킨 변경이 섞일 수 있다 |
| 충돌 나면 "내 거로 다 덮어" | 양쪽 비교 설명 → 내가 선택 | 다른 사람(또는 다른 세션)의 작업이 사라진다 |
| PR 설명 비우기 | 무엇을·왜·어떻게 확인했는지 | 나중에 왜 바꿨는지 아무도 모른다 |

## 6. 확인 방법과 막혔을 때

- 머지 후 main의 README에 합계 표가 보이는지 GitHub 웹에서 확인한다.
- T004가 0원으로 바뀌지 않았는지 확인한다.
- PR 만들기가 막히면 어떤 문구가 떴는지 Claude에게 전달하고, 공식 PR 안내를 따른다.

1. main이 아닌 새 브랜치에서 작업하고, 브랜치 이름과 변경 파일을 먼저 확인합니다.
2. 비교 화면에서 README만 바뀌었는지, 수치·T004 미확정 표시가 맞는지 읽습니다.
3. GitHub PR을 만들었다면 대상 main·Files changed·Checks를 보고 합칩니다. 로컬 merge만 했다면 GitHub PR 완료로 적지 않습니다.

**막혔을 때:** 브랜치를 만들었다는 답변 대신 실제 현재 브랜치를 확인합니다. 충돌은 양쪽 내용 비교부터 요청하고 한쪽 전체 덮어쓰기를 피합니다.

**이번 검토에서 확인한 범위:** 격리된 로컬 Git 브랜치·diff·merge를 실행해 확인했습니다. 새 GitHub 연습 PR 작성·머지는 별도 미검증입니다.

## 숙제

1. 새 브랜치에서 README 합계 표를 추가하고 PR을 만든다.
2. Files changed에서 변경된 파일 이름과 줄 수를 메모한다.
3. 직접 계산한 확정 합계와 README 숫자를 대조한 뒤 머지한다.

## 확인 퀴즈

4지선다 5문항입니다. 먼저 답을 고른 뒤 아래 해설을 확인하세요.

### Q1. PR의 뜻에 가까운 것은?

- A. 저장소 삭제 요청
- B. 비밀번호 변경
- C. 변경을 합치기 전에 검토받는 제안서
- D. 요금 결제

### Q2. 머지 전에 꼭 볼 화면은?

- A. Files changed(변경 파일)
- B. 프로필 사진
- C. 다른 저장소 목록
- D. 요금 페이지

### Q3. 변경 파일에 요청하지 않은 파일이 있으면?

- A. 그냥 머지한다
- B. 머지하지 말고 이유를 묻는다
- C. 저장소를 Public으로 바꾼다
- D. PR 설명을 지운다

### Q4. 충돌이 났을 때 올바른 요청은?

- A. "내 거로 다 덮어"
- B. "상대 거 다 지워"
- C. "저장소 새로 만들어"
- D. "양쪽 비교해서 설명하고 추천만 해줘"

### Q5. PR 설명에 쓰면 안 되는 것은?

- A. 바꾼 이유
- B. 확인한 방법
- C. 비밀키나 개인정보
- D. 미확정 항목

## 정답과 해설

1. **C** — PR은 "이렇게 바꿀게요"라는 제안이다.

2. **A** — 실제로 무엇이 바뀌었는지는 변경 파일에서만 확인할 수 있다.

3. **B** — 범위 밖 변경은 사고의 시작이다.

4. **D** — 어느 쪽을 남길지는 사람이 결정한다.

5. **C** — PR은 저장소에 접근하는 사람이 모두 본다.

## 념글 박제

PR = 머지 전 마지막 검문소. Files changed 안 읽고 누르면 검문소가 아니라 톨게이트 하이패스임.
