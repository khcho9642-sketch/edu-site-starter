# [강좌] C23. 훅 — 실행 전 차단과 실행 후 검사를 구분하자

> Claude Desktop의 **Code 로컬 프로젝트** 기준 · Windows 중심 · 공식 문서 확인: 2026-11-14  
> 먼저 읽을 강의: C03 · C14 · C22.  
> 원안: 사용자가 제공한 확장 기능 4부작의 훅 단원을 보완했습니다.

## 3줄요약

1. 훅은 정해진 이벤트가 생길 때 실행하는 검사다. 말로 주의하라고 하는 것과 다르다.
2. 실행 전 검사는 앞으로 할 작업을 막을 수 있지만, 실행 후 검사는 이미 한 작업을 되돌리지 않는다.
3. 가짜 파일에서 허용·차단·오류를 시험하고 원래 설정으로 돌리는 데까지가 실습이다.

## 1. 오늘의 목표

`protected-demo.md`는 고정하고 `normal-demo.md`만 바꾸도록 한다. 실제 비밀키 파일이나 운영 자료는 사용하지 않는다. 오늘 만든 검사는 **Edit·Write 도구로 지정한 파일을 수정하는 사례**만 다룬다. 명령 실행·다른 도구·외부 서비스까지 막는 보안 시스템이라고 부르면 안 된다.

| 상황 | 시점 | 의미 |
|---|---|---|
| 수정하기 전에 허용 여부 검사 | `PreToolUse` | 해당 도구 호출을 막을 수 있음 |
| 수정한 뒤 결과 검사·포맷 | `PostToolUse` | 이미 일어난 수정을 관찰·검사 |
| 답변을 마칠 때 완료 조건 확인 | `Stop` | 종료를 막으면 작업이 이어질 수 있음 |

종료 코드 2의 효과는 이벤트마다 다르다. 이번 **동기식 PreToolUse 명령 훅**에서는 차단 신호로 사용한다. 모든 이벤트와 비동기 훅에 같은 설명을 적용하지 않는다.

## 2. 준비물

1. C22에서 만든 로컬 연습 폴더를 Code 화면에서 선택한다.
2. [공통 샘플](실습자료/07_확장기능_공통샘플.md)의 가짜 보호 파일 두 개를 만든다.
3. 기존 `.claude/settings.json`이 있으면 **현재 파일을 먼저 읽고 연습 폴더 안에 백업**한다. 파일이 없었던 경우도 기록한다.
4. 사용 중인 Code 버전, 훅 지원 여부, 실제 사용할 수정 도구와 훅 실행 환경을 확인해 달라고 요청한다. 조직 정책이 막으면 실습 설계까지만 하고 기록한다.

```text
이 로컬 연습 폴더에서만 훅 실습을 준비해줘.
기존 .claude/settings.json 유무와 hooks 설정을 먼저 확인해줘.
있으면 덮어쓰기 전에 백업하고, 기존 항목을 유지하는 추가 계획을 보여줘.
현재 Code 환경에서 Edit·Write PreToolUse 훅을 실행하는 공식 설정과
PowerShell 실행 경로를 확인해줘. 아직 설정은 바꾸지 마.
```

## 3. 검사 파일 만들기

계획에서 경로와 수정 범위를 확인한 뒤 다음처럼 요청한다.

```text
.claude/hooks/protect-demo.ps1을 아래 예시로 만들어줘.
이 스크립트가 입력 JSON의 file_path를 검사하도록 해줘.
실제 회사 파일이나 다른 폴더는 건드리지 마.
설정은 아직 연결하지 말고 먼저 스크립트만 보여줘.
```

다음은 교육용 검사 예시다.

```powershell
$ErrorActionPreference = 'Stop'
try {
    $raw = [Console]::In.ReadToEnd()
    $event = $raw | ConvertFrom-Json -ErrorAction Stop
    if ($raw.TrimStart() -notmatch '^\{' -or $event -isnot [pscustomobject] -or
        $event.tool_input -isnot [pscustomobject] -or
        $event.tool_name -isnot [string] -or $event.tool_input.file_path -isnot [string]) {
        [Console]::Error.WriteLine('이벤트 객체와 도구 입력 형식을 확인하세요.')
        exit 2
    }
    $tool = [string]$event.tool_name
    if ($tool -notin @('Edit', 'Write')) {
        [Console]::Error.WriteLine('예상하지 않은 도구입니다. 실습 설정을 확인하세요.')
        exit 2
    }
    $filePath = [string]$event.tool_input.file_path
    if ([string]::IsNullOrWhiteSpace($filePath)) {
        [Console]::Error.WriteLine('파일 경로가 없어 실습 수정을 차단했습니다.')
        exit 2
    }
    $leaf = [System.IO.Path]::GetFileName($filePath.Replace('/', '\'))
    if ($leaf -ieq 'protected-demo.md') {
        [Console]::Error.WriteLine('교육용 보호 파일입니다. 이 수정은 차단합니다.')
        exit 2
    }
    exit 0
}
catch {
    [Console]::Error.WriteLine('검사 입력 처리에 실패했습니다. 실습 수정을 차단합니다.')
    exit 2
}
```

전체 경로나 입력 내용은 로그에 그대로 출력하지 않는다. 같은 이름의 파일은 어느 폴더에 있어도 막으므로 오탐 가능성이 있다. 경로별 권한 시스템으로 확장하려면 절대 경로 정규화, 링크, 다른 수정 수단까지 별도로 설계해야 한다.

배열이나 문자열처럼 예상과 다른 JSON 구조도 거절한다. Windows PowerShell 5.1을 사용한다면 한글이 있는 ps1을 UTF-8 BOM 형식으로 저장하고, PowerShell 7이라면 UTF-8을 사용한다. 실제 사용할 실행 파일·경로·공백 처리는 Code가 설명하게 한다. 사용자가 터미널에 명령을 입력하는 것이 필수는 아니다.

## 4. 설정을 연결하기 전에 무해하게 시험하기

```text
이 스크립트에 가짜 이벤트 JSON만 전달해서 단위 동작을 확인해줘.
실제 Edit·Write는 아직 호출하지 마.
1. Edit, normal-demo.md → 종료 코드 0
2. Write, protected-demo.md → 종료 코드 2
3. Edit, 파일 경로 없음 → 종료 코드 2
4. 잘못된 JSON → 종료 코드 2
5. 이벤트 객체 대신 배열 또는 file_path 숫자 입력 → 종료 코드 2
실제 종료 코드와 stderr를 표로 보고해줘.
파괴적인 명령을 실행해서 차단을 시험하지 마.
```

테스트가 맞아야 연결로 넘어간다. 검사 프로그램이 실행되지 않는 경우와 검사 프로그램이 정상 실행되어 차단하는 경우는 다르다.

## 5. 기존 설정에 추가하고 실제 호출 확인하기

```text
현재 환경의 공식 훅 설정 방식에 맞춰, 방금 스크립트를
Edit|Write에 대한 동기식 PreToolUse command 훅으로 연결해줘.
기존 설정을 유지하고 이 실습 항목만 추가해줘.
프로젝트의 절대 위치를 안전하게 참조하고 경로의 공백도 처리해줘.
스크립트 시작 실패·시간 초과 때의 실제 동작과 적용 조건도 설명해줘.
현재 버전이 지원하면 해당 차단 검사의 실패도 막도록 설정해줘.
지원되지 않는 설정값은 만들어 넣지 마.
```

앱이 새 세션이나 설정 재적용을 요구하면 그 안내를 따른다. 메뉴가 없는 환경에서 `/hooks` 메뉴가 있다고 단정하지 않는다. Code 설정 파일과 실제 훅 호출 기록으로 확인한다.

다음 두 요청을 **하나씩** 실행한다.

```text
normal-demo.md의 '수정 전'을 '수정 후'로 Edit 도구로 바꿔줘.
```

```text
protected-demo.md의 문장을 Edit 도구로 바꾸려고 한 번만 시도해줘.
훅이 차단하면 멈추고 이유를 보고해줘.
Bash·다른 도구·이름 변경으로 우회하지 마.
```

## 6. 예상 결과와 검수

| 검사 | 기대 결과 | 확인할 증거 |
|---|---|---|
| 일반 파일 수정 | 성공 | 실제 파일에 '수정 후' |
| 보호 파일 수정 | 차단 | 훅 차단 메시지 + 보호 파일 내용 동일 |
| 잘못된 가짜 입력 | 코드 2 | 스크립트 시험 결과 |
| 기존 설정 | 유지 | 변경 전후 차이에서 추가한 항목만 확인 |

도구를 호출하지 않고 Claude가 스스로 거절했다면 **훅 차단 검증은 미수행**이다. 오류나 시간 초과 때의 실제 호출은 아직 시험하지 않았다면 미확인으로 남긴다. 검사 스크립트의 `catch`는 실행 시작조차 못한 문제를 처리하지 못한다.

## 7. 해제와 복구

실습 훅 항목만 제거한다. 시작할 때 설정 파일이 없었다면 이번에 만든 내용만 있는지 확인한 뒤 처리한다. 다른 작업이 설정을 바꿨다면 백업을 통째로 덮어쓰지 말고 차이를 합친다. 훅 해제 후 같은 보호 파일의 무해한 수정이 허용되는지도 확인한다.

| 증상 | 확인할 것 |
|---|---|
| 정상 파일도 막힘 | 입력 JSON·도구 이름·파일 경로·실제 stderr |
| 보호 파일이 수정됨 | 해당 수정 도구가 매칭됐는지, 훅 호출 로그가 있는지 |
| 스크립트가 아예 실행 안 됨 | 실행 파일·경로·공백 처리·현재 버전의 셸 설정 |
| 끝나지 않고 반복함 | Stop 훅 등 다른 종료 검사가 연결됐는지 |

## 숙제

1. 실행 전 차단과 실행 후 검사의 차이를 사례로 적는다.
2. 허용·차단·잘못된 입력·실행 실패를 구분한 검수표를 만든다.
3. 이 훅이 막지 못하는 경로와 실습 설정을 제거한 방법을 기록한다.

- B. 파일이 존재하지 않는다
- C. 이미 실행된 작업의 결과를 검사한 것이다
- D. 항상 작업 실행을 막았다

- B. 모든 위험 명령 차단 성공

- D. 실제 훅 차단은 미확인으로 기록

- A. 일치하는 도구 호출에서 교육용 파일명을 검사하는 범위
- B. 모든 명령·외부 서비스의 수정 차단
- C. 컴퓨터 전체의 비밀정보 보호
- D. 이미 발송한 메일 취소

### Q5. 기존 설정이 다른 작업으로 바뀌었다면 복구 방법은?
- A. 백업으로 무조건 전체 덮어쓰기
- B. 차이를 확인하고 이번 실습 항목만 제거
- C. 모든 훅 폴더 삭제
- D. 권한 검사를 전부 끄기

## 정답과 해설

1. **B** — 도구가 실행되기 전의 검사 시점이다.
2. **C** — 사후 검사는 이미 일어난 작업을 자동으로 취소하지 않는다.
3. **D** — 자발적 거절과 훅이 실제 실행되어 차단한 결과는 다르다.
4. **A** — 이 예시가 확인하지 않는 다른 도구까지 보호한다고 말할 수 없다.
5. **B** — 다른 작업의 변경을 보존하면서 실습 변경만 되돌린다.
