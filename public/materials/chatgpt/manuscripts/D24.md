# [강좌] D24. 서브에이전트 — 만든 사람과 확인하는 사람을 나누자

> Codex 앱 선택 심화 · Windows 중심 · 공식 확인: 2026-11-14
> 먼저 읽을 강의: D14 · D22. D23의 실습 훅은 종료·해제한 뒤 진행합니다.

## 3줄요약

1. 서브에이전트는 특정 역할을 맡겨 결과를 받는 보조 작업자다.
2. 이번에는 회의록 결과를 직접 고치지 않는 검토자를 만든다.
3. '읽기만 해'라는 설명과 실제 도구 제한은 구분한다. 검토 의견도 원문과 대조한다.

## 1. 일을 나누는 이유

한 대화에 조사·작성·테스트·검토를 전부 넣으면 어느 단계에서 틀렸는지 찾기 어렵다. 역할을 나누면 입력과 완료 기준을 따로 줄 수 있다. 그렇다고 AI 검토가 사람 검토를 없애주는 것은 아니다. 같은 오해를 공유할 수도 있다.

| 역할 | 맡기는 일 | 이번 실습 |
|---|---|---|
| 조사 | 관련 자료와 구조 파악 | 입력 회의 A 확인 |
| 작성 | 기준에 따라 결과 생성 | D22의 스킬 결과 |
| 검토 | 누락·추정·근거 확인 | 일부러 틀린 결과 검사 |
| 사용자 | 근거 비교와 최종 판단 | 지적한 오류 3개 확인 |

일반적으로 위임할 때 필요한 배경과 파일을 명확하게 전달한다. 환경에 따라 대화 분기처럼 컨텍스트를 이어받는 방식도 있으므로 '모든 보조 작업자는 항상 완전한 백지'라고 외우지 않는다. 이번에는 필요한 입력을 지시문에 직접 적는다.

## 2. 준비물

1. D22의 입력/회의A.md와 [공통 오류 결과](/chatgpt-materials/extensions)를 준비한다.
2. 원문과 오류 결과의 작업 전 해시·내용을 기록한다. D23에서 실제 훅을 설치했다면 실습 항목을 해제한 뒤 진행한다.
3. Codex 앱에서 실제 서브에이전트 지원과 부모 작업의 권한을 확인한다. 웹 Work의 위임과 로컬 Codex의 사용자 정의 설정을 혼동하지 않는다.
4. 사용자 정의 이름은 `meeting-reviewer-demo`다. 같은 이름이 있으면 덮어쓰지 않는다.

## 3. 검토자 파일 만들기

Codex 사용자 정의 에이전트는 `.codex/agents/meeting-reviewer-demo.toml` 예시를 사용한다. Claude의 YAML `tools: Read, Glob, Grep`, `model: inherit`, `maxTurns`를 그대로 옮기지 않는다.

```toml
name = "meeting-reviewer-demo"
description = "회의 원문과 결과의 담당자·기한·실행 상태를 근거로 비교하는 검토자"
developer_instructions = """
두 입력 파일을 읽고 오류를 보고만 합니다.
파일 수정, 외부 연결, 메일 발송을 하지 않습니다.
근거ID·현재값·원문값·수정 제안을 제시합니다.
정상 항목과 확인하지 못한 부분도 구분합니다.
"""
```

특정 모델을 강제로 지정하지 않아 부모 설정을 따르게 한다. 위의 역할 지시는 기술적 읽기 전용 권한 설정이 아니다. 부모 권한·실제 도구 범위를 따로 확인해야 한다. 현재 지원되는 옵션으로 권한을 좁힐 수 없다면 “수정 금지 요청, 기술적 제한 미검증”으로 기록한다.

```text
이 연습 프로젝트의 사용자 정의 검토자 초안을 위 TOML 형식으로 보여줘.
기존 이름과 충돌하지 않는지, 현재 버전이 각 필드를 지원하는지 확인해줘.
에이전트 파일에 sandbox_mode나 MCP 설정을 넣어 권한이 독립적으로 바뀐다고 가정하지 마.
아직 에이전트 실행이나 전역 설정 변경은 하지 마.
```

## 4. 검토를 맡기기

먼저 부모 작업의 권한과 외부 연결 상태를 확인한다. 승인 방식만 바꾸는 것을 읽기 전용 격리라고 부르지 않는다. 지원되는 읽기 전용 환경을 선택할 수 있을 때는 그 적용 범위를 확인한다.

```text
실제 meeting-reviewer-demo 서브에이전트에 아래 검토를 위임해줘.
원문: 입력/회의A.md
대상: 검수/회의A_오류예시.md
기준: 실행/보류, 담당자·기한 원문 일치, 근거ID.
파일을 수정하지 말고 검토 결과만 반환해줘.
실제 보조 작업 이름·사용한 도구·완료 상태를 확인할 수 있게 보고해줘.
지원되지 않으면 메인 작업이 대신했다고 구분해줘.
```

활동 표시나 실제 위임 기록을 확인한다. 메인 답변에서 검토자 말투만 흉내 낸 것은 서브에이전트 실행 증거가 아니다.

## 5. 예상 결과

오류 예시에 심어 둔 문제는 세 가지다.

| 근거ID | 결과의 오류 | 원문 기준 |
|---|---|---|
| M02 | 수진에게 임의 배정 | 담당자 미정 |
| M03 | 기한을 12월 5일로 임의 입력 | 기한 미정 |
| M04 | 보류 항목을 실행 업무로 이동 | 보류 유지 |

M01은 정상이다. 총 오류 3개를 찾아야 하지만, 같은 문제를 여러 문장으로 반복했다고 오류 수가 늘어나는 것은 아니다. 원문에 없는 네 번째 문제를 만들어내도 통과가 아니다.

## 6. 읽기 전용이었는지 확인하기

1. 원문·오류 결과 파일의 작업 전후 내용 또는 해시를 대조한다.
2. 부모 작업의 실제 권한과 사용한 도구를 확인한다. TOML에 “읽기만”이라고 쓴 문장은 독립된 읽기 전용 환경을 만들지 않는다.
3. 외부 MCP 권한과 연결은 부모 설정을 따로 확인한다. 에이전트의 이름·설명·명령문만으로 차단됐다고 판정하지 않는다.
4. 수정 흔적이 없다는 관찰과 수정이 기술적으로 불가능했다는 주장을 구분한다.
5. 검토 결과 저장은 반환 뒤 메인 작업에 별도로 맡긴다. 원문 두 파일은 유지한다.

```text
검토 결과를 검수/회의A_검토기록.md로 메인 작업에서 저장해줘.
원문·오류예시는 바꾸지 마.
오류3개, 정상M01, 실제 위임 여부, 권한 검증 범위를 나눠 적어줘.
```

## 7. 막혔을 때와 대체 경로

| 증상 | 대응 |
|---|---|
| 에이전트를 찾지 못함 | 로컬 프로젝트 경로·파일명·이름을 확인하고 필요하면 새 세션 |
| 읽기 도구가 없다고 실패 | 현재 환경에서 유효한 도구 이름과 파일 접근 가능 여부 확인 |
| 메인 작업이 대신 리뷰 | 실제 위임 기록이 없으면 서브에이전트 실행 미확인으로 기록 |
| 검토자가 파일을 바꿈 | 도구 제한과 실제 실행자를 확인하고 샘플 원본에서 다시 시작 |
| 작업이 너무 길어짐 | 파일 두 개와 세 가지 기준처럼 범위를 줄임 |

지원되지 않으면 별도 대화에 두 파일과 검토 기준을 첨부한다. 이것은 **별도 대화 검토 실습**이다. 서브에이전트나 기술적 읽기 권한 제한이 적용됐다고 기록하지 않는다.

독립된 조사 두 개는 동시에 맡길 수 있지만, 같은 파일을 동시에 수정하게 하면 충돌한다. 오늘은 순차로 진행한다. 오타 한 줄을 고치는데 팀을 만들 필요는 없다.

## 화면 보며 따라 하기

**준비:** 회의A.md와 회의A_오류예시.md를 준비합니다.

[공통 실습 파일 ZIP 받기](/materials/walkthrough/cd-practice-starter.zip) · ZIP을 모두 푼 뒤 00_먼저읽기.md부터 확인합니다.

**내 화면에서:** Codex 에이전트 TOML의 역할 지시는 독립된 읽기 전용 권한이 아닙니다. 부모 작업의 권한도 확인합니다.

1. 원문과 검토 대상을 다른 파일로 구분하고 작업 전 내용을 보존합니다.
2. 검토자에게 근거ID·현재값·원문값·수정 제안을 요청합니다. 원문 두 파일은 수정하지 않도록 합니다.
3. 실제 위임 표시와 도구 제한을 확인하지 못하면 별도 대화 검토로 기록합니다. 결과 저장은 검토가 끝난 뒤 별도 작업으로 합니다.

**완료 확인**

- M02 담당자 추정 / M03 기한 추정 / M04 보류 오분류
- 오류 3개·정상 M01·입력 파일 보존

**막혔을 때:** 리뷰어라는 이름과 수정이 기술적으로 불가능한 환경은 다릅니다. 같은 오류를 두 번 말한 것을 오류 두 개로 세지 않습니다.

![따라 하기 화면](/materials/walkthrough/screens/review-result.png)

**이번 검토에서 확인한 범위:** 가짜 원문의 오류 3개와 정상 M01 기준을 대조했습니다. 그림은 검수 기준 예시이며 사용자 정의 서브에이전트 실행·기술적 읽기 전용 제한은 미검증입니다.

## 숙제

1. 조사 담당과 검토 담당의 입력·출력·도구·완료 기준을 각각 적는다.
2. 오류 3개를 원문으로 설명하고 M01이 정상인 이유도 적는다.
3. 말로 정한 역할과 실제로 제한한 권한을 두 칸으로 나눠 기록한다.

## 확인 퀴즈

4지선다 5문항입니다. 먼저 답을 고른 뒤 아래 해설을 확인하세요.

### Q1. 이번 검토자의 주된 역할은?

- A. 원문과 결과의 불일치를 근거와 함께 보고
- B. 원문을 결과에 맞게 수정
- C. 운영 서버 배포
- D. 사용자 계정 연결

### Q2. Codex 검토자가 수정하지 않았는지 판단할 증거는?

- A. 이름에 reviewer가 있음
- B. 조심한다는 답변
- C. 부모 권한·실제 호출 기록·작업 전후 파일 내용
- D. 결과가 김

### Q3. M02의 담당자를 수진으로 적었다면?

- A. 친절한 보완이므로 정상
- B. 원문에 없으므로 추정 오류
- C. 기한 오류만 존재
- D. 자동 저장하면 정상

### Q4. 사용자 정의 에이전트가 지원되지 않아 새 대화에서 검토했다면?

- A. 서브에이전트 실행 성공
- B. 기술적 읽기 권한 제한 성공
- C. MCP 연결 성공
- D. 별도 대화 검토 실습으로 기록

### Q5. 단순 오타 한 줄을 고칠 때 적절한 선택은?

- A. 필요하면 메인 작업에서 직접 수정
- B. 반드시 네 에이전트 동시 실행
- C. 모든 MCP 도구 연결
- D. 모든 파일 복사

## 정답과 해설

1. **A** — 수정과 검토를 나눠 오류의 근거를 확인한다.

2. **C** — 수정 금지 지시와 실제 권한·행동을 구분한다.

3. **B** — 원문에서 담당자가 미정이므로 임의 배정할 수 없다.

4. **D** — 가능한 학습 방식으로 대체하되 실제 실행 수단을 정확하게 적는다.

5. **A** — 위임 준비가 작업보다 길어질 정도면 직접 처리하는 편이 낫다.
