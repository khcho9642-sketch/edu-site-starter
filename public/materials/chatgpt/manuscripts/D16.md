# [강좌] D16. GitHub 사고 방지 — 진지하게 한 번

> Codex 앱 선택 심화 · Windows 중심 · 공식 확인: 2026-11-14
> 먼저 읽을 강의: D15.

## 3줄요약

1. 비밀키를 올렸으면 **파일 삭제가 아니라 키 폐기·재발급**이 먼저다.
2. 강제 푸시·기록 덮어쓰기·저장소 삭제는 **실행 전에 설명부터** 받는다.
3. 협업자는 **필요한 최소 권한**으로 초대하고, 정기적으로 점검한다.

## 1. 준비와 오늘의 결과

연습 저장소를 쓴다. 오늘 결과는 **내 저장소 안전 점검표 1장**이다. 사고 대응은 **가짜 키**(`FAKE_API_KEY=this-is-not-real-1234`)로 시나리오만 연습하고, 실제 키는 쓰지 않는다.

D15에서 만든 비공개 저장소를 기준으로 먼저 안전 원칙을 읽는다. 로컬 복제·제외 규칙 작성·푸시는 D17에서 진행한다. 아직 하지 않은 점검 항목은 **미실습**으로 남기고 D17이 끝나면 다시 확인한다.

## 2. 사고 시나리오: 비밀키를 올려버렸다

| 순서 | 할 일 | 왜 |
|---|---|---|
| 1 | **해당 서비스에서 키를 즉시 폐기하고 새로 발급** | 이미 복사됐을 수 있다. 키 자체를 죽이는 게 유일한 확실한 방법 |
| 2 | 새 키는 `.env`에만, `.gitignore` 확인(D17) | 같은 사고 반복 방지 |
| 3 | 저장소에서 파일 제거 | 단, **커밋 기록에는 남아 있다** |
| 4 | 기록에서 지우는 작업이 필요하면 공식 안내를 따르고, 혼자 판단이 어려우면 전문가와 상의 | 기록 정리는 협업자에게 영향을 준다 |
| 5 | 무엇이 언제 노출됐는지 메모 | 회사 자료라면 보안 담당에 보고 |

AI에게는 이렇게 묻는다.

> 가짜 키가 커밋에 들어간 상황이라고 가정할게. 내가 해야 할 일을 순서대로 정리해줘. 기록을 덮어쓰는 명령은 실행하지 말고 설명만 해줘.

GitHub에는 저장소에 올라간 비밀값을 탐지해 알려주는 기능이 있을 수 있다. 알림이 오면 무시하지 말고 1번부터 한다.

## 3. 되돌리기 어려운 작업 목록

| 작업 | 무엇이 위험한가 | 규칙 |
|---|---|---|
| 강제 푸시(force push) | 원격 기록을 덮어써서 다른 사람 작업이 사라질 수 있다 | 실습에서 쓰지 않는다. 필요하면 설명·영향 범위부터 |
| 기록 초기화(`reset --hard` 등) | 커밋 안 한 작업이 사라진다 | 실행 전 무엇이 사라지는지 목록 확인 |
| 저장소 삭제 | 이슈·PR·기록이 함께 사라진다 | 연습 저장소도 바로 지우지 말고 보관(Archive) 여부부터 검토 |
| 공개 범위 변경(Private → Public) | 전체 기록이 공개된다 | 기록에 비밀값·개인정보가 없는지 먼저 점검 |

## 4. 협업자 초대와 권한

1. 저장소 **Settings → Collaborators**(이름은 바뀔 수 있음)에서 초대한다.
2. 계정 종류를 구분한다. **개인 계정의 비공개 저장소는 협업자에게 읽기·쓰기 접근이 주어지며 읽기 전용 협업자 역할을 선택할 수 없다.** 조직 저장소에서 세분화된 역할이 제공될 때 필요한 최소 역할을 선택한다. 개인 비공개 저장소에 읽기만 필요하다는 이유로 쓰기 권한까지 줄 필요가 있는지 먼저 판단한다.
3. 프로젝트가 끝나면 초대를 정리한다.

## 5. 주의 사항

- 실제 비밀키·실제 카드내역·회사 자료로 사고 연습을 하지 않는다.
- 사고 화면을 캡처할 때 키 값·계정명·다른 저장소 이름을 가린다.
- AI가 강제 푸시나 기록 덮어쓰기를 제안하면 **이유와 영향 범위를 먼저 묻고**, 실행은 내가 판단한다.
- 회사 저장소라면 기술적으로 가능해도 **회사 보안 규정이 먼저**다.

## 6. 이렇게는 쓰지 말자

| ❌ 이렇게 하지 말자 | ✅ 대신 이렇게 | 이유 |
|---|---|---|
| 비밀키 커밋 → 파일만 지우고 끝 | 키 폐기·재발급부터 | 기록과 복사본에 남아 있다 |
| "깔끔하게 force push로 정리해" | 영향 범위 설명 → 내가 판단 | 다른 사람 작업이 사라질 수 있다 |
| 처음 보는 사람을 관리자 권한으로 초대 | 최소 권한, 끝나면 정리 | 저장소 삭제·설정 변경까지 가능해진다 |
| 오래된 Private 저장소를 점검 없이 Public 전환 | 기록의 비밀값·개인정보 점검 후 결정 | 과거 커밋까지 전부 공개된다 |
| 보안 알림 메일 무시 | 알림 내용 확인 → 위 2절 순서 | 이미 노출된 상태일 수 있다 |

## 7. 확인 방법과 막혔을 때

아래 점검표를 내 연습 저장소에 대해 채운다.

```
[ ] 공개 범위가 Private이다
[ ] .gitignore에 .env와 개인 자료 폴더가 있다
[ ] GitHub 웹에서 .env가 보이지 않는다
[ ] 협업자 목록에 모르는 사람이 없다
[ ] 협업자 권한이 필요한 만큼만이다
[ ] 비밀키를 올렸을 때의 대응 순서를 말할 수 있다
```

판단이 어려운 사고(실제 키 노출, 회사 자료 노출)는 혼자 처리하지 말고 서비스 공식 안내와 담당자에게 알린다.

## 화면 보며 따라 하기

**준비:** 가짜 키 시나리오와 안전 점검표를 준비합니다.

[공통 실습 파일 ZIP 받기](/materials/walkthrough/cd-practice-starter.zip) · ZIP을 모두 푼 뒤 00_먼저읽기.md부터 확인합니다.

**내 화면에서:** 공통 Git 점검 기준을 재사용합니다. 토큰을 채팅에 넣어 인증 오류를 해결하지 않습니다.

1. 실제 키를 쓰지 않고 노출 가정 → 폐기·재발급 → 보관·추적 점검 → 기록 대응 순서를 적습니다.
2. .gitignore에 적힌 것과 이미 추적 중인 것을 구분합니다. 아직 복제하지 않았다면 해당 항목은 미실습으로 남깁니다.
3. 개인 비공개 저장소의 협업자 권한과 조직 역할을 구분합니다. 실제 초대·공개 전환·강제 푸시는 하지 않아도 됩니다.

**완료 확인**

- 키 파일 삭제만으로 노출 대응이 끝나지 않음
- 커밋 예정 목록에 .env·개인자료가 없음

**막혔을 때:** 화면 캡처에 실제 키나 다른 저장소 이름이 보이면 공유하지 않습니다. 연습 점검표에 미실습이 있어도 사실대로 남기고 17강 뒤 다시 확인합니다.

![따라 하기 화면](/materials/walkthrough/screens/git-check.png)

**이번 검토에서 확인한 범위:** 격리된 가짜 Git 예제에서 제외 규칙·추적 목록을 시험했습니다. 실제 키 발급·폐기·협업자 권한 변경은 수행하지 않았습니다.

## 숙제

1. 위 점검표 6줄을 채운다.
2. 가짜 키 시나리오로 대응 순서를 내 말로 5줄 적는다.
3. 개인 저장소와 조직 저장소의 접근 권한 차이를 적는다. 실제 협업자 초대는 선택이며 필수 실습이 아니다.

## 확인 퀴즈

4지선다 5문항입니다. 먼저 답을 고른 뒤 아래 해설을 확인하세요.

### Q1. 비밀키를 GitHub에 올렸다. 가장 먼저 할 일은?

- A. 파일만 삭제한다
- B. 커밋 메시지를 바꾼다
- C. 해당 서비스에서 키를 폐기하고 새로 발급한다
- D. 저장소 이름을 바꾼다

### Q2. 파일을 삭제해도 남는 곳은?

- A. 커밋 기록
- B. 아무 데도 없음
- C. 내 이메일 서명
- D. 요금 페이지

### Q3. 강제 푸시를 제안받았을 때 올바른 태도는?

- A. 바로 실행
- B. 무조건 거절하고 저장소 삭제
- C. 비밀번호를 알려준다
- D. 이유와 영향 범위를 먼저 설명받고 판단한다

### Q4. 협업자 권한의 원칙은?

- A. 모두 관리자
- B. 필요한 최소 권한, 끝나면 정리
- C. 권한은 상관없다
- D. 비밀번호를 공유한다

### Q5. Private 저장소를 Public으로 바꾸기 전에 할 일은?

- A. 기록에 비밀값·개인정보가 없는지 점검한다
- B. 아무것도 안 한다
- C. 협업자를 모두 관리자로 바꾼다
- D. 보안 알림을 끈다

## 정답과 해설

1. **C** — 노출된 키는 이미 복사됐을 수 있다. 키를 죽이는 것이 먼저다.

2. **A** — Git은 기록을 남기는 도구다. 삭제도 하나의 기록일 뿐이다.

3. **D** — 되돌리기 어려운 작업은 사람이 영향 범위를 보고 결정한다.

4. **B** — 최소 권한 원칙을 따른다. 개인 비공개 저장소의 협업자는 읽기·쓰기 접근이 있으므로 읽기 전용 역할을 선택할 수 있다고 가정하지 않는다.

5. **A** — 공개 전환은 과거 기록까지 공개한다.
