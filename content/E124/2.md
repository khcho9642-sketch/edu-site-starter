## 5. 예상 결과

오류 예시에 심어 둔 문제는 세 가지다.

| 근거ID | 결과의 오류 | 원문 기준 |
|---|---|---|
| M02 | 수진에게 임의 배정 | 담당자 미정 |
| M03 | 기한을 12월 5일로 임의 입력 | 기한 미정 |
| M04 | 보류 항목을 실행 업무로 이동 | 보류 유지 |

M01은 정상이다. 총 오류 3개를 찾아야 하지만, 같은 문제를 여러 문장으로 반복했다고 오류 수가 늘어나는 것은 아니다. 원문에 없는 네 번째 문제를 만들어내도 통과가 아니다.

## 6. 읽기 전용이었는지 확인하기

1. 원문·오류 결과 파일의 작업 전후 내용 또는 해시를 대조한다.
2. 부모 작업의 실제 권한과 사용한 도구를 확인한다. TOML에 “읽기만”이라고 쓴 문장은 독립된 읽기 전용 환경을 만들지 않는다.
3. 외부 MCP 권한과 연결은 부모 설정을 따로 확인한다. 에이전트의 이름·설명·명령문만으로 차단됐다고 판정하지 않는다.
4. 수정 흔적이 없다는 관찰과 수정이 기술적으로 불가능했다는 주장을 구분한다.
5. 검토 결과 저장은 반환 뒤 메인 작업에 별도로 맡긴다. 원문 두 파일은 유지한다.

```text
검토 결과를 검수/회의A_검토기록.md로 메인 작업에서 저장해줘.
원문·오류예시는 바꾸지 마.
오류3개, 정상M01, 실제 위임 여부, 권한 검증 범위를 나눠 적어줘.
```

## 7. 막혔을 때와 대체 경로

| 증상 | 대응 |
|---|---|
| 에이전트를 찾지 못함 | 로컬 프로젝트 경로·파일명·이름을 확인하고 필요하면 새 세션 |
| 읽기 도구가 없다고 실패 | 현재 환경에서 유효한 도구 이름과 파일 접근 가능 여부 확인 |
| 메인 작업이 대신 리뷰 | 실제 위임 기록이 없으면 서브에이전트 실행 미확인으로 기록 |
| 검토자가 파일을 바꿈 | 도구 제한과 실제 실행자를 확인하고 샘플 원본에서 다시 시작 |
| 작업이 너무 길어짐 | 파일 두 개와 세 가지 기준처럼 범위를 줄임 |

지원되지 않으면 별도 대화에 두 파일과 검토 기준을 첨부한다. 이것은 **별도 대화 검토 실습**이다. 서브에이전트나 기술적 읽기 권한 제한이 적용됐다고 기록하지 않는다.

독립된 조사 두 개는 동시에 맡길 수 있지만, 같은 파일을 동시에 수정하게 하면 충돌한다. 오늘은 순차로 진행한다. 오타 한 줄을 고치는데 팀을 만들 필요는 없다.
