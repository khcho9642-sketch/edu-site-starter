## 렌더링과 비동기 결과 표시

렌더링은 데이터와 화면 구조를 실제 화면으로 표현하는 과정입니다. 서버 응답에는 시간이 걸리므로 요청 전·대기 중·성공·실패를 구분해야 사용자도 현재 상태를 이해할 수 있습니다.

| 상황 | 사용자에게 보여줄 것 |
| --- | --- |
| 처음 진입 | 화면의 목적과 다음 행동 |
| 조회 중 | 불러오는 중이라는 표시와 필요한 경우 취소 방법 |
| 자료 없음 | 실패와 구분해 “아직 작성한 글이 없습니다” 안내 |
| 조회 성공 | 자료와 기준 시각·필요한 상태 |
| 요청 실패 | 입력 보존, 확인된 오류와 다음 행동 |
| 응답을 받지 못함 | 실패를 단정하지 않고 저장 결과 확인 안내 |

### 비동기와 화면 갱신

비동기는 결과를 기다리는 동안 다른 일을 진행할 수 있는 방식입니다. 응답이 도착하면 상태를 갱신하고 화면에 반영합니다. 검색어를 빠르게 바꾸면 먼저 보낸 요청의 응답이 나중에 도착할 수 있으므로 현재 검색 조건과 맞는 결과인지 확인해야 합니다.

<div class="note"><b>렌더링 위치</b>
<p>브라우저가 주로 화면을 만드는 방식도 있고 서버가 화면을 준비해 보내는 방식도 있습니다. 어느 방식이든 사용자에게 표시하는 상태와 실제 저장 상태가 일치하도록 설계해야 합니다.</p></div>

<div class="tryit"><b>직접 해보기</b>
<p>저장 요청이 시간 초과됐을 때 “저장 실패”와 “저장 결과를 확인하지 못했습니다” 중 어떤 문구가 더 정확한지 설명하세요.</p>
<details><summary>예시 답 · 판단 기준</summary><p>서버에서 이미 저장됐을 가능성이 있으므로 결과 미확인이 정확할 수 있습니다. 재조회와 중복 방지 규칙이 필요합니다.</p></details></div>

## 라우팅과 화면 이동 설계하기

라우팅은 주소에 맞는 화면이나 처리 기능을 선택하는 규칙입니다. 메뉴 클릭만 생각하지 말고 주소 직접 입력·새로고침·뒤로 가기에서도 사용자가 어디에 있는지 알 수 있게 설계합니다.

| 주소·조건 | 보여줄 화면·행동 |
| --- | --- |
| /posts | 자신의 글 목록과 새 글 작성 버튼 |
| /posts/new | 빈 글 작성 화면 |
| /posts/15 | 접근 권한이 있는 15번 글의 상세 내용 |
| /posts/15/edit | 수정 권한을 확인한 뒤 편집 화면 |
| 없는 글 번호 | 찾을 수 없음을 알리고 목록으로 이동할 경로 제공 |
| 로그인 만료 | 인증이 필요함을 안내하고 허용된 범위에서 다시 이어갈 방법 제공 |

### URL에 담을 것과 담지 않을 것

검색어·페이지 번호처럼 공유하거나 다시 찾아갈 조건은 주소에 표현할 수 있습니다. 비밀번호·API 키·민감한 본문은 주소에 넣지 않습니다. 주소와 글 번호를 안다는 사실만으로 그 글을 볼 권한이 생기지는 않습니다.

<div class="note"><b>이동 전 확인</b>
<p>미저장 변경이 있을 때 경고만 반복하면 불편할 수 있습니다. 자동 저장 여부, 임시 보관, 이동 취소 등 지원할 방법을 정하고 실제 동작과 안내를 맞춥니다. 임시 보관과 서버 저장도 구분해서 표시합니다.</p></div>

<div class="tryit"><b>직접 해보기</b>
<p>글 편집 중 뒤로 가기를 눌렀을 때 사용할 안내 문구와 선택지를 적으세요.</p>
<details><summary>예시 답 · 판단 기준</summary><p>예: “아직 저장되지 않은 변경이 있습니다.” 선택지는 편집 계속·변경 버리고 이동. 저장 후 이동은 실제 저장 확인 후 진행합니다.</p></details></div>

## 반응형과 접근성을 함께 확인하기

반응형은 화면 크기에 맞게 배치를 조정하는 설계입니다. 접근성은 사용자가 키보드나 보조기기를 쓰더라도 기능을 이해하고 사용할 수 있게 하는 설계입니다.

| 개념 | 확인 방법 |
| --- | --- |
| 뷰포트·반응형 배치 | 작은 화면에서 입력창과 버튼이 잘리거나 서로 겹치지 않는지 확인 |
| 줄바꿈·가로 넘침 | 긴 제목·오류 문구·주소를 넣어 내용이 밖으로 벗어나지 않는지 확인 |
| 레이블 | 입력 항목의 이름을 표시하고 입력 요소와 연결 |
| 키보드·포커스 | 마우스 없이 입력·이동·실행할 수 있고 현재 위치가 보이는지 확인 |
| 색상·대비 | 오류를 빨간색만으로 표현하지 않고 문구·기호도 함께 사용 |
| 확대·읽기 순서 | 화면을 확대해도 핵심 동작이 가능하고 읽는 순서가 자연스러운지 확인 |
| 터치 대상 | 작은 화면에서도 인접한 버튼을 잘못 누르지 않게 간격과 크기를 검토 |

### 모바일에서의 우선순위

넓은 화면의 여러 열을 그대로 줄이기보다 필요한 정보부터 세로로 배치합니다. 예를 들어 제목·상태·예약 시각을 먼저 보여주고 추가 정보는 상세 화면으로 연결할 수 있습니다.

<div class="note"><b>확인할 대상은 실제 동작</b>
<p>모바일 그림이 한 장 있다는 것만으로 대응이 끝나지 않습니다. 긴 내용, 오류 메시지, 키보드 표시, 확대 상태에서도 작성과 저장을 완료해 봅니다.</p></div>

<div class="tryit"><b>직접 해보기</b>
<p>작성 화면을 키보드만으로 사용한다고 가정하고 첫 입력부터 저장 결과 확인까지 순서를 써 보세요.</p>
<details><summary>예시 답 · 판단 기준</summary><p>제목 → 본문 → 예약 여부 → 저장 버튼 → 결과 안내 순서가 자연스러운지 확인합니다. 실제 포커스 이동도 시험해야 합니다.</p></details></div>

## 업무 상태와 화면 상태 연결하기

업무 상태는 자료가 현재 어떤 단계인지 나타냅니다. 상태가 바뀌는 조건을 정해야 버튼 표시, 서버 처리, 데이터 기록이 같은 규칙을 따를 수 있습니다.

<div class="flow">
<div class="flow-box"><b>scheduled</b><span>예약 대기</span></div>
<div class="flow-arrow">→</div>
<div class="flow-box"><b>queued</b><span>큐 적재</span></div>
<div class="flow-arrow">→</div>
<div class="flow-box"><b>running</b><span>실행 중</span></div>
<div class="flow-arrow">→</div>
<div class="flow-box"><b>succeeded</b><span>모의 완료</span></div>
</div>
<p class="caption">예약의 실행 상태 예시입니다. 실행 중 응답을 받지 못하면 <b>unknown</b>(결과 확인 필요)이 됩니다. 초안의 검토 상태와 별도로 관리하며 실패·취소 경로는 생략했습니다.</p>

| 상황 | 화면에서 보여줄 것 |
| --- | --- |
| 초안 | 편집·저장·예약 가능 여부를 표시 |
| 활성 예약 있음 | 예약 시각·변경·취소 기능을 표시 |
| 실행 중 | 진행 상태를 알리고 변경 가능한 행동을 제한 |
| 완료·실패 | 실행 결과와 확인할 기록을 보여줌 |

### 어느 기록의 상태인지 적기

게시글의 상태와 예약의 상태, 실행 이력의 결과는 서로 다른 기록입니다. 예를 들어 예약 한 건에서 여러 번 시도할 수 있으므로 “실패 횟수”를 글의 상태 하나에 몰아넣지 않습니다. A2에서 기록 간 관계를, A3에서 실행 규칙을 자세히 설계합니다.

<div class="note"><b>버튼 숨기기만으로 끝나지 않는다</b>
<p>예약 버튼을 숨겨도 직접 요청이 들어올 수 있습니다. 현재 상태에서 허용되는 행동인지는 백엔드에서 다시 확인해야 합니다. 동시에 두 요청이 들어오는 경우도 별도로 처리합니다.</p></div>

<div class="tryit"><b>직접 해보기</b>
<p>활성 예약이 있는 글의 본문을 수정할 수 있게 할지 정하고 영향을 적으세요.</p>
<details><summary>예시 답 · 판단 기준</summary><p>예: 수정은 허용하되 예약 발행 시 어느 버전을 사용할지 명시한다. 예약 시점의 내용을 고정한다면 별도 버전 연결이 필요하다.</p></details></div>

## 클라이언트가 기억하는 것과 서버가 아는 것

브라우저에 보이는 값이 모두 서버에 저장된 것은 아닙니다. 화면의 임시 상태·브라우저 저장공간·서버의 기준 데이터를 구분하면 새로고침과 기기 변경에서 생기는 차이를 설명할 수 있습니다.

| 구분 | 성질과 주의점 |
| --- | --- |
| 화면 메모리 | 입력 중인 값 등을 보관. 화면을 닫거나 다시 읽으면 사라질 수 있습니다. |
| 로컬 스토리지 | 브라우저에 값을 보관. 동작·접근 범위와 민감정보 저장 여부를 검토합니다. |
| 세션 스토리지 | 주로 탭의 페이지 세션 범위에서 값을 보관합니다. |
| 쿠키 | 브라우저가 조건에 맞는 요청에 함께 보내는 값. 로그인 상태 관리 등에 쓰입니다. |
| 서버·DB | 여러 요청과 기기에서 사용할 기준 기록을 관리할 수 있습니다. |
| 캐시 | 빠르게 보여주기 위해 보관한 복사본. 최신 자료와 다를 수 있어 갱신 규칙이 필요합니다. |

### 클라이언트는 브라우저만이 아니다

모바일 앱이나 자동화 프로그램도 API를 요청하면 클라이언트입니다. 브라우저 입력 제한을 우회한 요청도 올 수 있으므로 자료형·권한·업무 규칙을 서버에서 확인합니다.

<div class="note"><b>내 컴퓨터에서 보인다는 뜻</b>
<p>로컬 화면이라도 외부 API나 AI로 데이터를 보내면 자료가 밖으로 이동합니다. 실행 위치와 저장 위치, 통신 목적지를 각각 확인해야 합니다. 로그인 토큰 등 민감한 값의 보관 방식은 보안 설계에서 결정합니다.</p></div>
