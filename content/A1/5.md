## 채워진 예시: 초안 저장 화면 설계

지금까지 배운 내용을 작은 설계 한 장으로 묶습니다. 예시의 규칙은 교육용 선택이며, 실제 프로젝트에서는 사용자의 업무와 제약에 맞게 확인하고 조정합니다.

| 항목 | 채워진 예시 |
| --- | --- |
| 목표·주소 | 작성자가 글을 잃지 않고 초안을 저장합니다. /posts/new |
| 입력·구성요소 | 제목·본문·저장 버튼·저장 결과 영역 |
| 검증 | 제목은 공백만 허용하지 않으며 예제 최대 100자. 서버도 같은 규칙 확인 |
| 요청·처리 | 화면은 입력을 전송하고, 서버는 작성자 권한과 규칙을 확인한 뒤 DB에 저장 |
| 성공 표시 | 서버가 돌려준 글 ID와 저장 시각으로 완료 표시. 목록에서 다시 확인 |
| 실패 표시 | 입력을 유지하고 문제 항목 또는 결과 미확인 상태를 안내 |
| 보관·권한 | DB의 글 작성자와 인증 사용자를 연결. 다른 사람의 글 접근은 서버에서 제한 |
| 확인 증거 | 저장 후 다시 조회한 제목·본문·작성자·상태를 확인 |

### 회계 업무에 옮기기

글 제목을 자료 요청 제목으로, 본문을 요청 내용으로, 예약 시각을 알림 시각으로 바꿀 수 있습니다. 추가로 회사별 자료 접근 범위, 첨부파일, 제출 기한 변경 이력을 설계해야 합니다.

<div class="note"><b>작은 완료 기준</b>
<p>버튼이 반응하는 것으로 끝내지 않습니다. 새로 조회해도 같은 데이터가 보이고, 다른 사용자는 허용되지 않은 자료에 접근할 수 없어야 합니다.</p></div>

<div class="tryit"><b>직접 해보기</b>
<p>이 설계에서 자동 저장을 추가한다면 변경해야 할 항목을 두 가지 이상 찾으세요.</p>
<details><summary>예시 답 · 판단 기준</summary><p>저장 시점·실패 안내·미저장 표시·요청 중복 방지·충돌 처리·서버 부하 등을 다시 정해야 합니다.</p></details></div>

## 자주 하는 실수와 바로잡는 방법

오류는 코딩 실력의 문제만으로 생기지 않습니다. 역할·상태·완료 기준을 서로 다르게 이해하면, 화면이 작동해 보여도 실제 업무는 끝나지 않을 수 있습니다.

| 흔한 오해 | 바로잡는 방법 |
| --- | --- |
| 프론트엔드가 서버와 반대말이다 | 화면 역할과 요청에 응답하는 역할을 구분하고 실제 실행 위치를 표시합니다. |
| 저장됨 문구가 뜨면 DB에도 저장됐다 | 성공 응답의 의미를 확인하고 다시 조회해 보관 결과를 확인합니다. |
| DB 관계도면 동작 순서도 알 수 있다 | ERD와 시퀀스도·상태도를 구분해 필요한 질문마다 사용합니다. |
| 화면에서 막았으니 잘못된 입력이 안 온다 | 서버에서도 자료형·권한·업무 조건을 검증합니다. |
| 오류가 나면 입력칸부터 초기화한다 | 사용자 입력을 유지하고 원인과 다음 행동을 알려줍니다. |
| 모바일은 화면을 작게 만들면 된다 | 정보 우선순위·터치·줄바꿈·키보드와 오류 상태를 실제로 확인합니다. |
| 로컬 화면이면 외부 전송이 없다 | API·AI 호출과 첨부파일 이동 경로를 따로 점검합니다. |

<div class="note"><b>실수 기록 방법</b>
<p>“사용자가 헷갈려 한다”보다 “저장 응답 전에 완료 문구가 떠서 사용자가 창을 닫았다”처럼 상황·행동·결과를 적습니다. 고친 뒤에는 같은 상황에서 문제가 사라졌는지 확인합니다.</p></div>

<div class="tryit"><b>직접 해보기</b>
<p>자신이 가장 혼동했던 개념 한 쌍을 고르고 차이를 예시로 설명하세요.</p>
<details><summary>예시 답 · 판단 기준</summary><p>예: UI는 제목 입력창과 버튼이고, UX는 입력·저장·재확인 과정에서 사용자가 경험하는 흐름이다.</p></details></div>

## 직접 실습: 내 업무의 작은 화면 만들기

아래 순서로 화면 한 개를 설계합니다. 많은 기능을 한꺼번에 넣기보다 입력에서 저장 결과 확인까지 한 흐름을 완성하세요. 빈칸을 채운 뒤 예시 답과 비교해 빠진 조건을 찾습니다.

| 순서 | 내가 작성할 내용 |
| --- | --- |
| 1. 목표 문장 | 누가 무엇을 입력하고 어떤 결과를 확인하는가? |
| 2. 화면 초안 | 필수 입력·주요 버튼·결과 영역을 간단히 배치 |
| 3. 입력 규칙표 | 각 항목의 의미·자료형·필수 여부·오류 문구 |
| 4. 처리 역할표 | 화면·서버·DB가 맡을 일을 각각 한 문장으로 작성 |
| 5. 상태표 | 입력 전·입력 중·처리 중·성공·실패·결과 미확인 |
| 6. 확인 시나리오 | 정상 저장·빈 값·연결 중단·새로고침 후 재조회 |

**예시 답: 자료 요청 등록** — 담당자가 요청 제목과 내용을 입력해 저장한 뒤 요청 목록에서 확인한다. 제목은 필수, 내용은 초안에서 선택이다. 화면은 입력을 안내하고 서버는 권한과 필수값을 검사한다. DB에는 요청 ID·작성자·제목·내용·상태를 저장한다.

<div class="note"><b>서로 검토할 기준</b>
<p>화면만 보고 다음 행동을 알 수 있는가? 성공과 실패를 구분하는가? 입력을 잃는 지점은 없는가? 서버에서 확인할 규칙이 빠지지 않았는가? 실제 저장 결과를 다시 확인할 수 있는가?</p></div>

<div class="tryit"><b>직접 해보기</b>
<p>설계에 없는 예외 상황 한 가지를 추가하고, 화면 안내와 서버 대응을 각각 적으세요.</p>
<details><summary>예시 답 · 판단 기준</summary><p>예: 로그인 만료. 화면은 입력을 보존할 수 있는 범위를 정하고 재로그인을 안내하며, 서버는 유효하지 않은 인증으로 저장하지 않습니다.</p></details></div>

## AI와 화면을 설계하고 검토하기

AI에게 화면을 요청하기 전에 목표·입력·업무 규칙·실패 상황을 함께 전달합니다. 받은 결과는 설명과 실제 동작을 비교하며, 확인하지 않은 사항을 완료로 기록하지 않습니다.

| 단계 | AI에 전달할 요청 예시 |
| --- | --- |
| 구조 정리 | 이 기능의 화면·클라이언트·백엔드·DB 역할과 실행 위치를 구분해 줘. 미확정은 가정으로 표시해 줘. |
| 화면 초안 | 제목·본문·저장 버튼·결과 영역을 배치하고, 각 항목이 필요한 이유를 설명해 줘. |
| 예외 설계 | 빈 제목·중복 클릭·연결 끊김·로그인 만료 때 입력 보존과 안내를 정리해 줘. |
| 개념 설명 | 이 코드에서 상태·이벤트·입력·출력이 무엇인지 예시 값으로 설명해 줘. |
| 검토 | 저장 문구와 실제 저장을 혼동한 부분, 화면에서만 권한을 검사한 부분을 찾아 줘. |
| 실행 확인 | 수정 전후 차이와 확인 절차를 적고, 직접 실행하지 않은 검사는 미실행으로 표시해 줘. |

### 짧은 요청문을 내 자료로 구체화

“좋은 화면 만들어 줘” 대신 “자료 요청 초안을 저장하는 화면이다. 제목은 필수이고 실패하면 입력을 유지한다. 로딩·오류·자료 없음 상태와 키보드 이동까지 설계해 줘”처럼 조건을 넣습니다.

<div class="note"><b>검토자가 맡을 일</b>
<p>업무 규칙이 맞는지, 사용자가 실제로 일을 끝낼 수 있는지, 민감한 자료가 어디로 가는지 확인합니다. 보기 좋은 화면과 기능 완성은 각각 따로 판단합니다.</p></div>
