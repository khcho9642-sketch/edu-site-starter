## 화면·처리·저장·실행 위치 구분하기

사용자는 하나의 앱을 보지만, 그 안에서는 여러 역할이 협력합니다. 역할을 구분하면 오류가 났을 때 어디를 살펴볼지, 데이터가 어디로 이동하는지 설명할 수 있습니다.

<div class="flow">
<div class="flow-box"><b>클라이언트 · 화면</b><span>입력 · 상태 · 결과 표시</span></div>
<div class="flow-arrow">API →</div>
<div class="flow-box"><b>백엔드 · 처리</b><span>권한 · 규칙 · 저장 요청</span></div>
<div class="flow-arrow">조회·저장 →</div>
<div class="flow-box"><b>데이터베이스</b><span>글 · 예약 · 실행 이력</span></div>
</div>
<p class="caption">작업은 스케줄러·워커가 예약을 확인하고 모의 실행한 뒤 결과를 기록합니다. 화면·백엔드·DB가 한 PC에 있을 수도, 서로 다른 환경에 있을 수도 있습니다. 실행 위치는 별도 결정입니다.</p>

### 같아 보이는 말을 구분하기

| 개념 | 뜻과 이 사례의 역할 |
| --- | --- |
| 프론트엔드 | 사용자가 보고 조작하는 부분. 글 입력창과 저장 결과를 보여줍니다. |
| 백엔드 | 입력 검증·업무 규칙·저장을 처리하는 기능. 작성 권한도 확인합니다. |
| 클라이언트 | 서비스에 요청하는 쪽. 여기서는 웹브라우저가 해당합니다. |
| 서버 | 요청에 응답하는 프로그램 또는 실행 컴퓨터. 내 PC도 서버가 될 수 있습니다. |
| DB·파일 저장소 | DB는 글·예약 등의 구조화된 기록, 파일 저장소는 첨부파일 등의 보관에 사용할 수 있습니다. |

<div class="note"><b>역할과 장소는 별개</b>
<p>백엔드는 처리 기능이고 클라우드는 자원을 제공받는 방식입니다. 백엔드를 내 컴퓨터에서 실행할 수도 있습니다. 프론트엔드도 서버에서 화면을 준비하는 방식이 있으므로, 화면과 실행 위치를 무조건 같은 뜻으로 외우지 않습니다.</p></div>

<div class="tryit"><b>직접 해보기</b>
<p>저장 버튼, 제목 검사, 글 기록, 실행 컴퓨터를 각각 어느 역할에 둘지 표시하세요.</p>
<details><summary>예시 답 · 판단 기준</summary><p>저장 버튼은 화면, 제목 검사는 화면과 백엔드, 글 기록은 DB, 요청에 응답하는 프로그램은 서버 역할입니다.</p></details></div>

## 그림마다 답하는 질문이 다르다

설계도를 하나만 그려서 모든 것을 설명하려고 하면 관계와 순서가 섞입니다. 먼저 무엇을 설명할지 정한 뒤 그 목적에 맞는 그림이나 표를 선택합니다.

| 산출물 | 답하는 질문 | 게시글 앱 예시 |
| --- | --- | --- |
| 시스템 구성도 | 무엇이 어디에 있고 연결되는가? | 브라우저·API 서버·DB·워커 |
| 업무 흐름도 | 누가 어떤 일을 어떤 순서로 하는가? | 작성 → 검토 → 예약 |
| 시퀀스도 | 구성요소가 어떤 순서로 요청하는가? | 화면 → 서버 → DB → 화면 |
| 상태 전이도 | 어떤 조건에서 상태가 바뀌는가? | 예약 대기 → 실행 중 → 성공·실패 |
| ERD | 어떤 기록이 몇 개씩 연결되는가? | 회원 한 명과 글 여러 개 |
| 데이터 사전 | 각 데이터 항목의 의미와 조건은? | 제목은 문자·필수·길이 제한 |
| 화면 초안 | 사용자가 무엇을 보고 입력하는가? | 제목·본문·저장 버튼의 배치 |

### 한 요구를 여러 관점으로 보기

“자기 글만 예약한다”는 요구는 화면에서는 예약 버튼, API에서는 권한 검사, 데이터에서는 글 작성자 연결, 테스트에서는 다른 사용자의 예약 거부로 표현됩니다. 서로 다른 산출물이 같은 규칙을 설명해야 합니다.

<div class="note"><b>헷갈리지 않기</b>
<p>ERD의 선은 업무 실행 순서가 아닙니다. 회원과 글의 관계를 그린 것만으로 저장 요청이 언제 발생하고 실패하면 무엇을 보여줄지는 알 수 없습니다.</p></div>

<div class="tryit"><b>직접 해보기</b>
<p>“저장 중에 인터넷이 끊겼다”를 설명하려면 어떤 자료를 함께 볼지 고르세요.</p>
<details><summary>예시 답 · 판단 기준</summary><p>요청 순서를 보는 시퀀스도와, 저장 중·결과 미확인·재조회 상태를 보여주는 화면 상태표가 필요합니다.</p></details></div>

## UI보다 먼저 사용자의 일을 정하기

UI는 버튼과 입력창 같은 접점이고, UX는 사용자가 일을 끝내는 과정의 경험입니다. 화면에 많은 기능이 있어도 다음 행동을 찾기 어렵거나 결과를 확인할 수 없으면 사용하기 어렵습니다.

| 구분 | 게시글 작성 화면의 예시 |
| --- | --- |
| 사용자와 목표 | 작성자가 초안을 잃지 않고 저장한 뒤 다시 수정합니다. |
| 시작 조건 | 로그인되어 있고 새 글 작성 메뉴에 들어왔습니다. |
| 주요 행동 | 제목·본문 입력 → 저장 → 저장된 글 확인 |
| 성공 기준 | 저장된 글 ID와 수정 시각을 확인하고 목록에서도 같은 글을 찾습니다. |
| 실패·중단 상황 | 필수값 누락·권한 만료·연결 끊김·페이지 이동 전에 미저장 변경이 있습니다. |
| 우선순위 | 새 글 저장이 핵심. 색상 테마 변경 같은 부가 기능은 뒤로 미룹니다. |

### 정보 구조와 행동 순서

정보 구조는 내용을 어떤 메뉴와 묶음으로 나눌지 정하는 일입니다. 사용자 동선은 실제 목표를 이루기 위해 어떤 화면을 거칠지 정하는 일입니다. “글 목록 → 글 작성 → 저장 확인”처럼 목적이 있는 흐름으로 검토합니다.

<div class="note"><b>채워진 개선 예시</b>
<p>기존: 저장 후 버튼만 원래대로 돌아옵니다. 개선: “저장됨” 표시와 수정 시각을 보여주고, 목록으로 돌아가 다시 열 수 있게 합니다. 성공 여부를 사용자가 추측하지 않도록 합니다.</p></div>
